# O `-r` abaixo aponta para o `requirements.in` (a fonte), NÃO para o
# `requirements.txt` (o compilado), e isso é deliberado: o compilado é resolvido
# para Linux e lista `uvloop` e `httptools` sem marker de plataforma — pelo
# `uvicorn[standard]`. Instalá-lo no Windows morre na hora, e aqui o
# desenvolvimento é no Windows. É também o comportamento que este arquivo sempre
# teve; antes da troca de nomes, `-r requirements.txt` já era a fonte.
#
# Quem precisa do ambiente EXATO da imagem instala o compilado direto
# (`pip install -r requirements.txt`), que é o que o Dockerfile faz.
-r requirements.in

# Gera o `requirements.txt` compilado e é o que o gate "Compilado de dependências
# em dia" do CI executa. FIXADO porque o gate compara a saída dele com o versionado:
# instalado sem versão, uma release que mude o cabeçalho gerado ou a estratégia
# de resolução reprovaria o CI sem uma linha de código ter mudado — e a correção
# não estaria em lugar nenhum do diff. Mesma razão de todo o resto estar fixado.
#
# 7.6.0 -> 7.6.1 porque fixar o pip-tools NÃO bastava: ele importa
# `pip._internal.utils.compat.stdlib_pkgs`, um interno PRIVADO do pip, e o passo
# anterior do mesmo job rodava `python -m pip install --upgrade pip` sem pino.
# Quando o pip 26 removeu esse símbolo, o `pip-compile` passou a morrer em 0,3 s
# com `ImportError` — o gate ficou vermelho sem ninguém ter tocado em
# dependência alguma, que é exatamente o que o parágrafo acima queria evitar.
# O pino protegia contra o pip-tools mudar, não contra o pip mudar embaixo dele.
#
# O pip PASSOU a ser fixado no workflow (`pip==...` no ci.yml e no relock.sh),
# que era a saída sugerida aqui. `test_nenhum_pip_install_sem_versao_no_ci`
# impede que ele volte a ficar solto.
pip-tools==7.6.1
